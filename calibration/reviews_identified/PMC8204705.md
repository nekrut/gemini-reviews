### 1. SUMMARY AND OVERALL IMPACT STATEMENT

Kosakovsky Pond et al. present version 2.5 of `HyPhy` (HYpothesis testing using PHYlogenies), an open-source C++14 and HyPhy Batch Language (HBL) software platform for fitting continuous-time Markov substitution models and conducting evolutionary hypothesis tests on multiple sequence alignments. The 2.5 release refactors the core engine and standard library to support non-interactive command-line execution via keyword arguments, package-manager installation (`bioconda` and `Homebrew`), standardized Markdown summary reports and machine-readable JSON outputs paired with an interactive JavaScript visualization suite (`hyphy-vision`), and multicore/distributed parallelization (`SIMD`, `OpenMP`, `MPI`). The authors also describe a continuous-integration testing pipeline covering $>90\%$ of HBL functions alongside an automated cross-package likelihood verification suite (`testiphy`) that checks `HyPhy` likelihood evaluations against `IQ-TREE`, `RAxML`, and `MrBayes`. All source code, documentation, test suites, and web services (`Datamonkey`) are freely available under open-source licenses.

As a software architecture and ecosystem update, `HyPhy 2.5` exemplifies modern scientific software engineering, particularly in its automated cross-platform likelihood verification (`testiphy`), reproducible JSON output schema, and accessible Conda/web deployment. The primary limitation of the manuscript is the complete absence of quantitative empirical benchmarks: although the Abstract and text claim "substantial performance and stability enhancements," scalability to alignments with thousands of sequences, and parity of tuned multicore CPU routines against GPU acceleration, the paper includes no runtime, memory, or parallel-scaling tables comparing `HyPhy 2.5` against earlier `HyPhy` releases (e.g., v2.2/v2.3) or competing tools (`PAML`/`codeml`). In addition, the "Analyses and Models Supported" section cites the methodological papers for its core selection and rate tests without naming the actual algorithms (`BUSTED`, `MEME`, `aBSREL`, `FEL`, `FUBAR`, `RELAX`, `GARD`, `LEISR`) or summarizing their recommended dataset regimes. Both omissions can be easily addressed by adding a comparative benchmark figure/table and a structured catalog table of stock analyses.

### 2. SPECIFIC CONCLUSIONS AND ASSESSMENT OF SUPPORT

* **HyPhy 2.5 provides a modular, pipeline-ready command-line interface with standardized JSON/Markdown reporting and automated likelihood verification: [Well Supported].**  
  The architectural improvements—keyword-driven CLI arguments, working-directory-relative path resolution, `conda install hyphy` packaging, JSON output integration with `hyphy-vision`, $>90\%$ HBL unit-test coverage, and `testiphy` likelihood cross-checks against `IQ-TREE`, `RAxML`, and `MrBayes`—are concrete, verifiable, and directly address reproducibility bottlenecks in comparative sequence analysis.

* **HyPhy 2.5 supports a flexible class of continuous-time Markov models with arbitrary parameter constraints, rate variation, and simulation capabilities: [Well Supported].**  
  The platform's support for site-, branch-, and branch-site random effects, adaptive and conditionally dependent discrete rate distributions, hidden Markov models for spatial rate autocorrelation, penalized likelihoods, and parametric/non-parametric sequence simulation is well established across the cited literature and open-source HBL library.

* **HyPhy 2.5 delivers substantial computational performance enhancements over previous releases and scales to alignments containing thousands of sequences: [Moderately Supported].**  
  While the implementation of `SIMD` vectorization, `OpenMP` multithreading, `MPI` distribution, and variational Bayes approximations (`FUBAR`) provides a sound algorithmic basis for faster execution, the manuscript provides no quantitative benchmark data (wall-clock runtimes, peak memory footprint, OpenMP strong/weak scaling efficiency, or version-to-version speedups from `HyPhy 2.2` to `2.5`) to quantify these gains across representative alignments.

* **Popular HyPhy analyses do not significantly benefit from GPU acceleration compared with tuned multicore CPU optimizations: [Fragile].**  
  In "Optimized for Larger Data Sets," the authors state that *"the majority of popular analyses implemented in HyPhy do not significantly benefit from GPU acceleration compared with tuned multicore CPU optimizations (in our hands at least, also see Izquierdo-Carrasco et al. 2013)."* No empirical comparison on modern GPUs (e.g., via `BEAGLE v3`, which is cited in the next sentence) versus `OpenMP`/`SIMD` CPU execution for 61-state codon models (where matrix exponentiation and partial-likelihood inner products are compute-dense) is presented to support this statement, and the 2013 nucleotide-model citation predates modern tensor/FP64 GPU architectures.

### 3. CONSTRUCTIVE AND DOABLE SUGGESTIONS FOR IMPROVEMENT

#### 1. Add a Quantitative Runtime, Memory, and Parallel Scaling Benchmark Table
* **WHY:** Readers and pipeline developers need empirical metrics to evaluate the claimed performance gains of `HyPhy 2.5` over `HyPhy 2.2/2.3` and to know what alignment sizes ($N$ taxa $\times L$ codons) are tractable on a desktop versus an HPC cluster.
* **WHAT:** Benchmark wall-clock runtime, peak RAM, and `OpenMP` thread scaling (1, 4, 8, 16, 32 cores) for the core stock analyses across small ($N=25$), medium ($N=250$), and large ($N=2,500$) codon alignments.
* **HOW:** Run `FEL`, `MEME`, `BUSTED`, `aBSREL`, `RELAX`, and `FUBAR` using `HyPhy 2.5` and `HyPhy 2.2/2.3` (and `PAML codeml` where applicable) on three standard empirical or simulated alignments of $L=500$ codons with $N \in \{25, 250, 2500\}$ sequences. Report a summary table or two-panel figure showing version-to-version speedup factors, memory consumption, and multicore parallel efficiency.

#### 2. Include a Structured Reference Table of Stock Analyses and Their CLI Keywords
* **WHY:** In the "Analyses and Models Supported" section (paragraph 1), the text cites eight foundational papers (`Murrell et al. 2015`, `Pond and Frost 2005a`, `Murrell et al. 2012, 2013`, `Smith et al. 2015`, `Wertheim et al. 2015`, `Pond et al. 2006`, `Poon et al. 2007`, `Spielman and Pond 2018`) without naming the corresponding methods (`BUSTED`, `FEL`/`SLAC`, `MEME`, `FUBAR`, `aBSREL`, `RELAX`, `GARD`, `BGM`, `LEISR`) or their `hyphy <method>` command-line invocations.
* **WHAT:** Add a concise lookup table mapping each prepackaged analysis name and CLI keyword to its biological question, statistical model/test, practical dataset-size scale, and reference.
* **HOW:** Insert a table (Table 1) listing each stock method (`hyphy busted`, `hyphy meme`, `hyphy absrel`, `hyphy fel`, `hyphy slac`, `hyphy fubar`, `hyphy relax`, `hyphy gard`, `hyphy bgm`, `hyphy leisr`), its target of inference (gene-wide, episodic site, branch-site, pervasive site, relaxation of selection, recombination, coevolution, relative rates), and recommended taxon range.

#### 3. Document Backward-Compatibility Changes and Numerical Tolerances in `testiphy`
* **WHY:** The Abstract and Introduction note that `HyPhy 2.5` is "mostly backward compatible" with "several obscure features that have been deprecated, and more rigorous runtime error condition checking," and the Software Engineering section introduces `testiphy` for cross-package likelihood comparisons. Specifying the exact log-likelihood agreement tolerance and deprecated HBL constructs helps existing HBL script authors migrate safely.
* **WHAT:** State the numerical log-likelihood tolerance achieved in `testiphy` across `IQ-TREE`, `RAxML`, and `MrBayes` and link to a migration guide for legacy HBL scripts.
* **HOW:** In the "Software Engineering" section, report the maximum absolute log-likelihood discrepancy (e.g., $|\Delta \ln L| < 10^{-5}$) verified by `testiphy` across nucleotide, protein, and codon models, and provide a direct URL or appendix bullet list summarizing deprecated HBL 2.2 syntax versus HBL 2.5 equivalents.
